# Goal3：当前候选基础收益的详细离线验算

本文展开 [第二份报告第 9 节](goal3_static_disassembly2.md) 中已经复算正确的两组结果。证据来自此前保存的断点快照；本次仅读取本地文件、做整数运算，没有重新采集游戏现场，没有调用游戏函数或进行游戏测试。

## 1. 本次具体在验证什么

需要验证的是以下关系：

```text
基础收益 R = 单次商品量 q × 单位净收益 p
```

游戏保存的不是这里显示的小数，而是放大 100000 倍的整数。落实到内存字段，当前两组样本应满足：

```text
candidate[+10] = trunc(candidate[+38] × candidate[+18] / 100000)
```

其中偏移为十六进制，三个字段均为 64 位有符号整数，`trunc` 表示向零截断。当前输入均为正数，因此也等于整数除法取商。

验算过程分为四步：从快照取出候选字节；按正确字段类型解码；根据反汇编复算；与快照中已经保存的 `R` 比较。**输入 `q、p` 和用于比对的 `R` 分别取自不同字段，计算时没有用 `R` 反推输入。**

本次闭合的是“已保存的 q、p → 基础收益 R”这一段。它并不等于从州修正、市场价格、关税、补助等原始输入重新计算出了 `q、p`，也不等于最终评分 `D` 的所有分项已经验证。

## 2. 数据来源与候选定位

### 2.1 数据来源与候选地址

主要依据：

- [候选、常量及寄存器快照](../Output/goal3_scoring_20261002/constants_snapshot.json)：`reads.items` 中地址为 `3A5FF822A80` 的记录包含 320 字节，即 `0x140` 字节的条目。
- [商品对象快照](../Output/goal3_static_20261002/fields.json)：用于把商品指针对应到 `wood` 和 `fine_art`。
- [收益计算反汇编](../Output/goal3_static_20261002/function_7FF777CEC080.md)：用于确定字段含义、乘法与截断步骤。
- [最终执行反汇编](../Output/goal3_static_20261002/function_7FF777CED470.md)：用于确认快照断点位于候选重算之后。

条目地址 `entry=0x3A5FF822A80`。候选定位如下：

| 候选 | 条目内偏移 | 候选地址 | 商品指针 | 商品 ID / 名称 |
| --- | --- | --- | --- | --- |
| 增加 | `+B0` | `3A5FF822B30` | `3A4012E4A60` | 10 / `wood`（软木） |
| 减少 | `+F8` | `3A5FF822B78` | `3A4012E94C0` | 52 / `fine_art`（艺术品） |

例如，软木的 `q` 地址为 `entry+B0+38=3A5FF822B68`。这里的加法使用十六进制偏移，不能把 `38` 当作十进制 38。

两候选 `+08` 的方向字节都是 `00`。模式在 `+2C`，按 32 位整数读取：软木是 `01 00 00 00`，艺术品是 `00 00 00 00`。两者 `+30` 的短缺指标都是 0。方向、模式与短缺字段不是同一个字段，不能混读。

### 2.2 如何从候选地址解码出商品名称

名称不是由地址数值计算出来的，也不是按商品 ID 查一张预先假定的名称表。实际证据链是：**候选地址 → 读取候选首部的商品指针 → 读取该指针指向的商品对象 → 解码对象内保存的英文商品键名**。本次用两份已保存快照重现这一过程，无须重新读取游戏内存。

**第一步：读取候选 `+00` 的 8 字节，按小端无符号整数还原指针。**

| 候选地址，即读取位置 | 原始 8 字节 | 解码后的指针 |
| --- | --- | --- |
| `3A5FF822B30` | `60 4A 2E 01 A4 03 00 00` | `0x000003A4012E4A60` |
| `3A5FF822B78` | `C0 94 2E 01 A4 03 00 00` | `0x000003A4012E94C0` |

例如第一行字节按高位到低位书写为 `00 00 03 A4 01 2E 4A 60`，得到 `0x3A4012E4A60`。这 8 字节表示地址，不是名称字符。随后必须读取地址指向的内容；读取候选附近的其他字节不能代替这次指针解引用。

这与 [Refresh 反汇编](../Output/goal3_static_20261002/function_7FF777CEBDA0.md) 一致：`+11FBDE3` 的 `mov rax,[r14]` 从候选首部取指针，紧接着 `+11FBDE6` 的 `movsxd rbx,dword ptr [rax+10]` 从该对象 `+10` 取商品索引。它支持“候选 `+00` 指向商品对象”的解释；名称则由下面的对象快照提供。

**第二步：在商品对象快照中找到对应地址的记录，分别解码 ID 与名称。**

`fields.json` 的 `items` 中，恰有地址为 `3A4012E4A60`、`3A4012E94C0` 的两条字节记录。对每条记录，`+00` 指记录起始的商品对象地址，不再是候选地址。

| 内容 | 相对商品对象偏移 | wood 对象 | fine_art 对象 |
| --- | --- | --- | --- |
| 商品 ID，4 字节 | `+10` | `0A 00 00 00` → 十进制 10 | `34 00 00 00` → 十进制 52 |
| 本次名称字符起点 | `+18` | `3A4012E4A78` | `3A4012E94D8` |
| 字符及终止字节 | 从 `+18` 开始 | `77 6F 6F 64 00` | `66 69 6E 65 5F 61 72 74 00` |

这里 `+10` 与 `+18` 也是十六进制偏移。`goods+10` 的四字节数值是 ID；`goods+14` 到 `goods+17` 的其他字节不属于 ID，也不属于名称。本次没有依靠那些字节识别商品。

**第三步：把名称字节按 ASCII 解码，到第一个 `00` 截止。**

```text
wood：
    地址 3A4012E4A78 起：77 6F 6F 64 00
    字符逐个对应：      w  o  o  d  字符串终止
    得到英文键名：      wood

fine_art：
    地址 3A4012E94D8 起：66 69 6E 65 5F 61 72 74 00
    字符逐个对应：      f  i  n  e  _  a  r  t  字符串终止
    得到英文键名：      fine_art
```

`00` 是终止字节，不是字符 `0`；字符 `0` 的 ASCII 值是 `30`。这两个名称只含 ASCII 字符，因此用 UTF-8 解码也得到相同结果。

快照还提供了相互印证的结构信息：商品对象 `+28` 的 8 字节分别为 4、8，与名称长度一致；`+30` 的 8 字节都为 15。这与“16 字节内联字符区、长度字段和容量字段”的短字符串布局相符。因此，本次可以直接读取对象 `+18` 的内联字符，**不需要把 `goods+18` 的前 8 字节再次解释成字符串指针**。这是针对这两个短名称的判断；本轮没有恢复长名称时的完整存储规则，不能直接将该读取方式推广到所有对象。

**第四步：用本地配置确认键名，并区分英文键名与中文显示名称。**

本机 `game\common\goods\00_goods.txt` 第 126 行和第 588 行分别包含 `wood = {`、`fine_art = {`，支持上述字节确实是商品键名。ID 则直接来自对象 `+10`，不是按配置文件的行号或排列次序推算。

中文不在上述名称字节中。本机 `game\localization\simp_chinese\goods_l_simp_chinese.yml` 第 16 行是 `wood: "木材"`，第 45 行是 `fine_art: "艺术品"`。所以前文沿用的“软木”是分析中的中文称呼，**本机简体中文本地化对 `wood` 的实际名称是“木材”**；不能说是把这些内存字节直接解码成了“软木”。两条路径分别是：

```text
候选 → 商品指针 → 对象内字符 → wood / fine_art
英文商品键名 → 本地化文本匹配 → 木材 / 艺术品
```

下面的代码可在仓库根目录重现指针与英文键名的解码，仅读取已保存的两个 JSON 文件：

```python
# 功能：离线从候选快照追踪商品指针，并解码本次两个短商品名称。
import json
import struct
from pathlib import Path

snapshot = json.loads(Path(
    "Output/goal3_scoring_20261002/constants_snapshot.json"
).read_text(encoding="utf-8"))
entry = bytes.fromhex(next(
    x["value"] for x in snapshot["reads"]["items"]
    if int(x["address"], 16) == 0x3A5FF822A80
))
goods_snapshot = json.loads(Path(
    "Output/goal3_static_20261002/fields.json"
).read_text(encoding="utf-8"))

for offset, expected in ((0xB0, (10, "wood")), (0xF8, (52, "fine_art"))):
    # 候选首部保存商品指针；按该地址寻找商品对象的快照记录。
    pointer = struct.unpack_from("<Q", entry, offset)[0]
    goods = bytes.fromhex(next(
        x["value"] for x in goods_snapshot["items"]
        if int(x["address"], 16) == pointer
    ))
    goods_id = struct.unpack_from("<i", goods, 0x10)[0]
    # 本次两个对象的短名称均内联于这 16 字节中。
    chars = goods[0x18:0x28].split(b"\x00", 1)[0]
    name = chars.decode("ascii")
    assert (goods_id, name) == expected
    assert len(chars) == struct.unpack_from("<Q", goods, 0x28)[0]
    print(f"goods_ptr={pointer:X} goods_id={goods_id} name={name}")
```

输出为：

```text
goods_ptr=3A4012E4A60 goods_id=10 name=wood
goods_ptr=3A4012E94C0 goods_id=52 name=fine_art
```

## 3. 从原始字节还原 q、p、R、D

### 3.1 字段类型与小端顺序

本次相关数值按 x64 小端序保存：最低有效字节在前。以软木的单位净收益为例：

```text
内存字节：A7 71 08 00 00 00 00 00
整数十六进制：0x00000000000871A7
整数十进制：553383
显示值：553383 / 100000 = 5.53383
```

这些字节应作为 `int64` 解码，不能当作 IEEE 754 双精度浮点数。候选 `+08` 的方向则只读一个字节，`+2C` 的模式只读四个字节。

## 4. 为什么两个整数相乘后，只除一次 100000

令缩放因子 `F=100000`，内存中的整数记为 `Q、P`：

```text
q = Q / F
p = P / F
q × p = Q × P / F²
```

乘积如果还要存成同一种五位定点数，就要再乘回一个 `F`：

```text
R_raw = trunc((q × p) × F)
      = trunc(Q × P / F)

R_display = R_raw / F
```

所以，**计算内存结果时除一次 100000；把内存结果显示成小数时再除一次 100000。** 这是两个不同步骤。

数值意义也有区别：`q` 是一次贸易容量调整对应的商品量，`p` 是每单位商品的净收益，二者相乘得到这一次容量单位对应的基础收益。它不是当前整条贸易的总收益。

## 5. 软木：从输入到内存结果逐步比对

### 第一步：读取输入

```text
Q = 1500000   → q = 15
P = 553383    → p = 5.53383
```

### 第二步：做整数乘法

```text
Q × P = 1500000 × 553383
      = 830074500000
```

### 第三步：恢复定点缩放，检查商与余数

```text
830074500000 = 8300745 × 100000 + 0

商 = 8300745
余数 = 0
R_raw_calculated = 8300745
```

余数为零，所以这一乘法步骤没有损失小数精度。

### 第四步：与快照比较

```text
计算结果：8300745
快照中 candidate+10：8300745
差值：0

计算结果的小端字节：C9 A8 7E 00 00 00 00 00
快照中的小端字节：C9 A8 7E 00 00 00 00 00
```

整数和 8 字节编码均一致。显示值为：

```text
8300745 / 100000 = 83.00745
15 × 5.53383 = 83.00745
```

这里的“没有损失精度”只针对这一乘法步骤；不表示输入 `p` 在更早的价差与税补计算中没有经过截断。

## 6. 艺术品：截断发生在哪里

### 第一步：读取输入

```text
Q = 225000    → q = 2.25
P = 2723615   → p = 27.23615
```

### 第二步：做整数乘法

```text
Q × P = 225000 × 2723615
      = 612813375000
```

### 第三步：恢复定点缩放，保留整数商

```text
612813375000 = 6128133 × 100000 + 75000

商 = 6128133
余数 = 75000

未截断的原始结果 = 6128133.75
截断后的原始结果 = 6128133
```

注意 `6128133.75` 仍处于“放大 100000 倍”的尺度。把截断前后都换成显示值：

```text
数学乘积：2.25 × 27.23615 = 61.2813375
定点结果：6128133 / 100000 = 61.28133
截掉部分：61.2813375 - 61.28133 = 0.0000075
```

因此，余数 75000 不是损失了 0.75 的显示值，而是损失了 0.75 个原始整数单位，即 `0.75/100000=0.0000075`。

### 第四步：与快照比较

```text
计算结果：6128133
快照中 candidate+10：6128133
差值：0

计算结果的小端字节：05 82 5D 00 00 00 00 00
快照中的小端字节：05 82 5D 00 00 00 00 00
```

如果采用四舍五入保留五位小数，`61.2813375` 会变成 `61.28134`，对应原始整数 6128134，比快照大 1。当前快照与反汇编均支持截断得到 6128133。

## 7. 用反汇编再次核对计算方式

### 7.1 输入与输出字段直接对应

收益函数 `+11FC080` 中，`RSI` 保存候选指针。相关指令为：

```asm
+11FC251  mov r9,[rsi+38]       ; 读取 Q：单次商品量的定点整数
+11FC255  mov rcx,[rsi+18]      ; 读取 P：单位净收益的定点整数
...
+11FC27A  imul r9,rcx           ; 得到整数乘积 Q×P
+11FC27E  mov rax,29F16B11C6D1E109
+11FC288  imul r9              ; RDX:RAX 保存有符号乘法的 128 位结果
+11FC28B  sar rdx,0E           ; 对高 64 位算术右移 14 位
+11FC28F  mov rax,rdx
+11FC292  shr rax,3F           ; 取得符号校正位
+11FC296  add rdx,rax          ; 校正有符号除法的截断方向
+11FC299  mov [rsi+10],rdx      ; 写入基础收益的定点整数
```

这里没有显式 `idiv 100000`，而是编译器用常量乘法、取高位、移位和符号校正实现除以 100000。不能因为看见 `29F16B11C6D1E109` 就把它解释成某个收益系数。

### 7.2 两组样本都走直接乘法分支

`+11FC259…+11FC278` 在乘法前检查两个操作数的范围。指令中的 `0xB504F333=3037000499`、`0x16A09E666=6074000998` 用于范围判断；本次四个输入均为正数且小于 3037000499，因此不跳往 `+11FC29F` 的分解计算路径。

这既支持直接使用上面的整数乘积，也避免把大数分支的截断细节混入本次验算。本文的逐指令复现仅针对这两组已确认走直接路径的样本。

### 7.3 连常量乘法和移位也能复现

设 `N=Q×P`，`M=0x29F16B11C6D1E109`。对当前正数样本：

```text
high = floor(N × M / 2^64)
shifted = high >> 14
符号校正位 = 0
R_raw = shifted
```

离线计算如下：

| 中间量 | 软木 | 艺术品 |
| --- | ---: | ---: |
| N = Q×P | 830074500000 | 612813375000 |
| 高 64 位 high | 135999406080 | 100403343360 |
| high 算术右移 14 位 | 8300745 | 6128133 |
| 符号校正位 | 0 | 0 |
| 最终 R_raw | 8300745 | 6128133 |

结果同时与“除以 100000 取商”以及快照中的 `candidate+10` 相同。当前数值下，这不只是小数显示相近，而是原始整数逐位一致。

## 8. 最终评分 D 与净修正的核对边界

快照中的 `D` 来自 `candidate+20`，与 `R` 是不同字段。

```text
软木：
    D_raw - R_raw = 9921745 - 8300745 = 1621000
    显示差值 = 1621000 / 100000 = 16.21000

艺术品：
    D_raw - R_raw = 6128133 - 6128133 = 0
```

这两项减法同样可以精确验证，但其证据强度要分开看：

| 内容 | 本次核对结果 |
| --- | --- |
| q、p 的快照值与小数换算 | 已从字节重新解码 |
| q×p 的乘法、截断及 R 写入格式 | 已离线复算，与保存的 R 完全一致 |
| D 的快照值 | 已重新解码，并非本次从评分全部输入重新计算 |
| D−R 的净修正 | 已按原始整数相减核对 |
| q 的全部上游州修正 | 本次未独立重建 |
| p 的价差、关税、补助来源 | 本次未逐项复算 |
| D−R 中每个政策/市场修正项 | 本次未逐项复算 |

两候选短缺指标都是 0，所以按已还原的 `300×H` 公式，短缺加分为 0。执行反汇编显示，两候选分别在 `+11FD59D`、`+11FD5B6` 重算，快照停在其后的 `+11FD5C9`；因此这里读取的是刷新后的评分。

软木的 `+16.21` 不能直接标成“补助加分”，因为它是其余修正项的合计。艺术品净修正为零也不能证明每个分项都为零，它们可能相互抵消。

## 9. 可重复执行的纯离线核对代码

在仓库根目录运行以下 Python 代码即可复算。它只读取已有 JSON 文件，不连接 Cheat Engine，不访问游戏进程。整数运算不依赖浮点格式化或 `round()`。

```python
# 功能：从已有快照解码候选并离线核对基础收益，不访问游戏进程。
import json
import struct
from pathlib import Path

SCALE = 100000
MAGIC = 0x29F16B11C6D1E109
LIMIT = 0xB504F333


def read_i64(data, offset):
    """读取小端有符号整数；入参为字节序列和偏移，返回 64 位字段值。"""
    return struct.unpack_from("<q", data, offset)[0]


def verify_candidate(entry_bytes, candidate_offset):
    """核对正数样本；入参为条目字节和候选偏移，返回验算结果字典。"""
    c = entry_bytes[candidate_offset:candidate_offset + 0x48]
    q = read_i64(c, 0x38)
    p = read_i64(c, 0x18)
    stored_r = read_i64(c, 0x10)
    stored_d = read_i64(c, 0x20)

    # 本次样本符合直接乘法路径；不以此代替所有大数或负数路径。
    assert 0 < q <= LIMIT and 0 < p <= LIMIT
    product = q * p
    calculated_r, remainder = divmod(product, SCALE)

    # 对当前正数输入复现常量乘法、高位提取和移位，符号校正为零。
    high = (product * MAGIC) >> 64
    instruction_result = high >> 14
    assert instruction_result == calculated_r == stored_r
    assert struct.pack("<q", calculated_r) == c[0x10:0x18]

    return {
        "q_raw": q, "p_raw": p, "product": product,
        "remainder": remainder, "high64": high,
        "r_raw": calculated_r, "d_raw": stored_d,
        "net_adjustment_raw": stored_d - stored_r,
    }
```
