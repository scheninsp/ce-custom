# 刷新候选函数进出口数量输出分析

本文回答 `Docs\important_notes\todo.md` 的第二个问题：刷新候选函数最终以怎样的形式输出对单项商品的进出口数量调整。

## 结论先行

可以用 `Docs\vic3_doc_copy\trace_capcity9.md` 的新信息补充并收紧此前的推断。当前最完整、且与反汇编和游戏配置一致的模型是：

```text
商品基础交易量 base = goods.traded_quantity
若商品没有单独配置 traded_quantity，则 base = GOODS_DEFAULT_TRADE_QUANTITY

州级数量修正 modifier = state_trade_quantity_mult 的运行时聚合值
单次商品量 q = max(MINIMUM_GOODS_TRADED_QUANTITY,
                   base × (1 + modifier))

单次成功增加：对应商品统计表 += q
单次成功减少：对应商品统计表 -= q
累计变化：Σ成功增加的 q - Σ成功减少的 q
```

程序内部通常使用 `100000` 倍定点整数保存数量，因此：

```text
1.0 件商品 = 100000
0.5 件商品 = 50000
q_raw = q × 100000
```

这里的 `q` 是“消耗 1 个贸易容量单位时对应的商品数量”，不是容量表中的数值。容量账本一次通常只增减 1 个容量单位，而商品表一次增减的是商品自己的 `q`。

因此，刷新候选函数不会直接输出一条已经完成的“进口木材 15”或“出口艺术品 2.25”订单。它只把一次容量调整对应的商品数量写入候选 `candidate+0x38`；候选通过评分、容量、资格和保护期等判断并成功执行后，执行函数才把这个步长写入相应商品统计表。

## 一、数量公式的来源

### 1. 反汇编确认的写回链

在 `victoria3.exe+11FBDC9` 附近的数量调用点：

1. 从 `candidate+0x00` 读取商品指针；
2. 解析候选关联的州指针；
3. 调用 `victoria3.exe+122AB50`；
4. 将返回的定点数量写入 `candidate+0x38`。

`+122AB50` 的调用参数没有候选评分、贸易方向或当前容量，因此它计算的是“该州与该商品在一次容量单位上的商品步长”，不是最终成交总量。

伪代码对应 `FakeCode\trade_candidate_functions.md` 中的 `CalculateQuantityPerCapacity`（`victoria3.exe+122AB50`）。

### 2. 商品基础值来自 `traded_quantity`

`trace_capcity9.md` 提供了此前缺失的配置层对应关系：商品定义中的 `traded_quantity` 就是每个贸易容量单位对应的基础商品量。

```text
每单位商品占用的贸易容量 = 1 / traded_quantity
每 1 单位贸易容量承载的商品量 = traded_quantity
```

本地游戏配置中的例子：

| 商品 | `traded_quantity` | 每单位商品占用容量 | 每 1 容量单位对应商品量 |
| --- | ---: | ---: | ---: |
| `fabric`（织物） | 10 | 0.1 | 10 |
| `tea`（茶叶） | 5 | 0.2 | 5 |
| `clippers`（帆船） | 3.5 | 约 0.2857 | 3.5 |

因此，观测到“1 单位织物占 0.1 容量”时，刷新候选数量步长的基础值应理解为 `10`，而不是 `0.1`。同理，茶叶的基础步长是 `5`，帆船的基础步长是 `3.5`。界面将帆船容量占用约显示为 `0.3`，属于显示精度造成的四舍五入。

如果商品定义没有单独设置 `traded_quantity`，则使用：

```text
GOODS_DEFAULT_TRADE_QUANTITY = 10
```

该默认值位于本地 `game/common/defines/00_defines.txt` 的 `GOODS_DEFAULT_TRADE_QUANTITY` 定义中。它解释了为什么大量普通商品的基础交易量可能为 `10`。

### 3. 州级修正来自贸易数量修正

`+122AB50` 已确认从州关联修正容器读取 selector `0x97`，然后执行：

```text
q_raw = FixedMultiply(base_raw, 100000 + modifier_raw)
q_raw = max(q_raw, MINIMUM_GOODS_TRADED_QUANTITY)
```

`trace_capcity9.md` 在生产方式配置中找到了对应的脚本字段：

```text
state_trade_quantity_mult = -0.5
state_trade_quantity_mult =  0.5
state_trade_quantity_mult =  1.0
```

这与反汇编的定点公式一致，说明该修正应按“相对基础交易量的倍率修正”理解：

```text
modifier =  0.5  → q = base × 1.5
modifier = -0.5  → q = base × 0.5
modifier =  1.0  → q = base × 2.0
```

当前可以把 selector `0x97` 高概率解释为州的贸易数量修正或其聚合值；但属性注册表尚未完全恢复，因此仍不把 `0x97` 的正式内部字段名写死。

## 二、执行时如何形成进出口数量

### 1. 刷新只生成单次步长

`Refresh` 计算出的 `candidate+0x38` 是单次容量操作对应的商品数量。它不包含：

- 本轮剩余操作预算；
- 当前可用容量总量；
- 候选评分决定的成交次数；
- 同一商品在其他路线或其他州的数量。

所以 `q` 不是某条贸易路线的最终存量，也不是一次 `UpdateStateTrades` 必然产生的总量。

### 2. 增加和减少使用同一个商品步长

数量函数本身没有贸易方向参数。相同州、相同商品和相同修正下，增加与减少、进口与出口使用相同的 `q`；方向只影响：

- 候选评分和收益计算；
- 商品数量写入哪一套方向表；
- 执行时使用加号还是减号。

`+11FD470` 的正常路径可概括为：

```text
增加路径：对应方向商品表、市场商品表、全局商品表 += q
减少路径：对应商品表 -= q
容量账本：另外增加或减少 1 个容量单位，并编码方向
加权价值表：增加路径可能写入 q × advantage；这不是商品数量
```

因此，不能把容量表中的 `+100000` 或 `-100000` 解释成 `+1` 或 `-1` 件商品；也不能把 `q × advantage` 当成进出口数量。

### 3. 一次更新的累计数量

`+11FD470` 一次调用最多完成一次减少和一次增加，减少与增加共用成功预算。上层 `+131C2B0` 会在仍有预算时反复选择候选并执行。

在 `q` 不变的理想情况下：

```text
累计商品变化 = (成功增加次数 - 成功减少次数) × q
```

如果商品配置、州修正或相关运行时对象发生变化，则必须按每次成功操作的实际 `q` 逐次求和：

```text
累计商品变化 = Σ每次成功增加的 q_i - Σ每次成功减少的 q_i
```

这也解释了为什么一次容量替换可以同时表现为例如：

```text
木材 +15，艺术品 -2.25
```

两者各自对应 1 个容量单位，但商品数量不需要相等，也不需要按件数相等；容量相等是账本层面的约束。

## 三、样本与配置的交叉验证

现有候选样本中：

| 商品 | 基础交易量 | 州级修正 | 候选 `q` | 计算 |
| --- | ---: | ---: | ---: | --- |
| `wood`（木材） | 10 | `+50%` | 15 | `10 × 1.5` |
| `fine_art`（艺术品） | 1.5 | `+50%` | 2.25 | `1.5 × 1.5` |

这两个样本与新的配置解释完全一致：基础值对应商品的 `traded_quantity`（或默认值），`q` 再乘以州贸易数量修正。

它们证明的是候选的单次步长；只有观察到 `+11FD470` 成功返回并对商品表做前后差分，才能证明该次确实发生了对应的商品数量调整。

## 四、必须避免的混淆

### 1. `traded_quantity` 与 `convoy_cost_multiplier` 不是同一个概念

`traded_quantity` 决定“每 1 个贸易容量单位对应多少商品”。

`convoy_cost_multiplier` 决定运输贸易路线的船队/运输成本。即使两个字段都出现在商品定义中，也不能用后者推导刷新候选的商品数量。

例如，织物、茶叶和帆船的 `convoy_cost_multiplier` 与它们的容量占用比例没有直接等价关系；容量占用应由 `1 / traded_quantity` 计算。

### 2. 预算、容量、商品数量是三个独立量

条目预算为 `11` 不等于商品数量 `11`；容量上限为 `126` 也不等于 `126` 件商品。预算决定最多可以尝试多少次，容量账本决定可以占用多少贸易容量，候选 `q` 决定每次成功操作改变多少商品。

## 五、当前仍不能完全确认的内容

1. selector `0x97` 的正式属性注册名，以及多个 `state_trade_quantity_mult` 来源叠加时的精确运行时聚合规则。
2. `goods+0x50` 与脚本字段 `traded_quantity` 的完整加载转换过程，包括定点缩放和异常商品的边界处理。
3. 方向表、市场表、全局表分别对应哪个 UI 数值、贸易路线字段或市场汇总字段。
4. `+12295A0` 返回的初始操作预算的完整来源、缩放和边界。
5. `UpdateStateTrades` 的严格调度频率，不能仅凭存在 `state_weekly_trades_add` 就断言每次调用恰好对应一个游戏周。
6. 在容量已满、失败扣预算、保护期、无有效候选和商品标志异常等路径中，执行函数返回值、容量变化和商品表写入是否始终完全等价。

## 六、下一步验证建议

要把“单次步长模型”推进到“UI 最终进出口量模型”，应优先采集以下证据：

1. 对同一州同一商品执行一次确定成功的增加和一次确定成功的减少，在执行前后同时读取候选 `q`、容量表、方向表、市场表和全局表。
2. 选择 `traded_quantity` 明确不同的商品（如织物、茶叶、帆船），验证基础步长分别接近 `10`、`5`、`3.5`，再切换贸易数量修正验证倍率。
3. 追踪 `+12295A0`，确定预算的真实来源，并记录失败路径是否消耗预算。
4. 追踪 `UpdateStateTrades` 的调用者，确认一次外层调用与游戏周或其他 Tick 周期的关系。
5. 从 UI 或贸易路线对象读取显示值，建立各内部商品表到“进口量/出口量”显示值的明确映射。

## 当前回答的边界

现在可以较有把握地确认：

- `Refresh` 将一次容量单位对应的商品数量写入候选 `+38`；
- 该数量的基础值来自商品 `traded_quantity`，未配置时使用 `GOODS_DEFAULT_TRADE_QUANTITY`；
- `state_trade_quantity_mult` 通过州级修正改变该基础值；
- 成功执行一次容量调整时，商品统计表按 `±q` 更新，累计结果是所有成功步骤的逐次求和；
- `traded_quantity` 不应与 `convoy_cost_multiplier` 混淆。

尚不能完全确认的是 selector `0x97` 的正式字段映射、所有商品对象的加载细节、各统计表与 UI 的精确对应，以及预算和调度的完整语义。
