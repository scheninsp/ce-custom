## 三、逐项问题

### R1 — 最终核对不可用时，manifest 和退出码仍像核对成功

**优先级：P2。属性：本次新增。**

**定位：**

- 计划 `L774–789`：`check_residue`。
- 计划 `L853–857`：收尾后直接计算 `complete/failed/aborted` 和退出码。
- 计划 `L1277`：验收仅要求存在 `ceResourcesBefore` 且没有 `residueWarning`。
- 计划 `L1308`：把没有 `residueWarning` 与前后计数一致并列作为验收条件。

**问题：**

`check_residue` 捕获 `TransportError` 或 `ToolError` 后，只打印 WARN 并返回，不保存“未完成核对”的结构化状态。若所有指令已成功导出，而最后一次 overview 超时：

- `run_exports` 返回 `0`；
- `manifest.status` 为 `complete`；
- manifest 不含 `residueWarning`；
- `4.3` 中的资源核对断言仍通过。

因此，“没有警告字段”既可能表示“计数相同”，也可能表示“根本未取得结束计数”。这与 `4.4` 中“超时/传输断开退出码 3”的统一表述也不一致。

**离线复现结果：**

使用单目标正常导出，在第三次 overview（前检查、后检查、最终资源检查）注入超时：

```json
{
  "case": "final_overview_timeout",
  "exitCode": 0,
  "status": "complete",
  "residueWarningPresent": false,
  "overviewCalls": 3
}
```

**建议修订：**

- 持久化独立的 `residueCheck`，至少区分 `unchanged`、`changed`、`unavailable`、`skipped`，保留 `before`、取得的 `after`、时间和错误原因。
- 明确最终核对失败的退出码：按当前文档应返回 `3`；如果有意把它定义为“不影响数据导出成功的信息性检查”，就同步修改退出码说明，并确保验收不能把 `unavailable` 当作 `unchanged`。
- `4.3` 应显式断言核对状态为 `unchanged`，而不是仅断言某字段不存在。
- 增加“只在最终 overview 失败”的测试；当前超时测试发生在地址采集阶段，覆盖不到此分支。

### R2 — “无论成败都核对资源”的保证没有进入异常退出路径

**优先级：P2。属性：本次新增。**

**定位：**

- 计划 `L25`、`L1239`：宣称所有地址处理完后“无论成败”都核对。
- 计划 `L849–853`：逐文件写入、进度写入之后，才执行 `check_residue`。
- 计划 `L904–923`：`main` 的异常处理和 `finally`。

**问题：**

`check_residue` 只是 `run_exports` 正常走到循环末尾时的一条语句。以下情况会提前离开函数：

- 写 `opcode_*.md`、`manifest.json` 或 `index.md` 失败；
- 用户在循环或写入阶段按 Ctrl+C；
- 其他进入外层错误处理的异常。

外层 `main` 会先关闭客户端，再更新失败状态，没有执行或记录资源核对。对于仍可正常通信的客户端，这是确实遗漏了可执行的收尾检查；对于已经断开的客户端，也没有明确记录“无法检查”，不能声称所有失败均完成核对。

**离线复现结果：**

在首个目标完成两次会话检查后，令文件写入抛出 `PermissionError`：

```json
{
  "case": "opcode_file_write_failure",
  "exception": "PermissionError",
  "overviewCalls": 2,
  "finalResidueCheckPerformed": false
}
```

**建议修订：**

- 将收尾审计放入由 `main` 管理的统一结束流程，在释放可用客户端前执行，保证只执行一次。
- 前提是已建立资源基线；客户端健康时尝试检查，已断开/已失效时标记 `unavailable` 或 `skipped`，不盲目重连。
- 对用户中断明确采用有界收尾或直接记录跳过原因，避免为了审计额外阻塞很久。
- 保留原始失败退出码，例如写入失败仍为 `2`、中断仍为 `130`；审计异常不应覆盖原始原因。
- 磁盘不可写时，不保证 manifest 一定能更新，文档应说明结构化记录是尽力保存，并保留英文 stderr 诊断。
- 增加写入失败、Ctrl+C、已有连接失效的收尾测试。

R1 解决“核对尝试后失败却未记录”，R2 解决“核对根本没有被执行”；只修正其中一项不能覆盖另一项。

### R3 — 替换重复运行检查时，丢失了对第一次产物的保护验证

**优先级：P2。属性：本次回归。**

**定位：**

- 计划 `L1247`：以 manifest 含运行 ID/时间戳为由，取消文件哈希检查。
- 计划 `L1261`、`L1296–1301`：只保存第一次指令表，然后比较两次表格。
- 上一版相应代码保存第一次目录内各文件的哈希，第二次运行后再次读取**第一次目录**进行核对。

**问题：**

原哈希检查的目的不是比较“第一次文件是否等于第二次文件”，而是确认“第一次已产生的文件在第二次运行后没有变化”。第二次文件的 runId/时间戳不同，不会影响这个检查。

新代码只在第一次运行结束时读一次旧文件。第二次运行后，它读取第二次目录并与内存中的旧表格比较，完全不再检查第一次目录。于是即使第二次运行改坏了第一次的文件，只要新表格相同，验收仍会通过。

**离线复现：**

将 `4.3` 原样验收代码放到临时目录，用假执行器生成两次合格输出；第二次额外把第一次某个 opcode 文件改写为 `CORRUPTED OLD EXPORT`：

```json
{
  "case": "repeat_acceptance_old_output_corruption",
  "acceptancePassed": true,
  "firstRunFileCorrupted": true
}
```

**建议修订：**

- 恢复对第一次运行目录的文件名集合及内容哈希检查：第一次结束后记录，第二次结束后重新读取同一目录核对。
- 保留两次目录不同、每次文件名集合及 201 条窗口检查。
- 两次指令表比较只能作为另一个可选检查，不能替代旧文件完整性检查。
- 当前比较还包含 CE 地址显示和 `extra` 注释。若保留跨运行相等要求，应明确代码/符号/显示内容稳定的前提；否则合理的显示变化也可能被误判成导出隔离失败。
- 增加“第二次运行改动第一次目录”的验收反例，要求必须失败。

### R5 — 启动握手被 Ctrl+C 打断时，客户端可能没有被关闭

**优先级：P2。属性：上一版已存在；本次新增的清理保证使它更需要明确处理。**

**定位：**

- 计划 `L172–197`：`McpClient.start` 仅通过 `except Exception` 执行失败清理。
- 计划 `L889`：`client = McpClient(...).start()`。
- 计划 `L910–912`：只有 `client is not None` 才调用 `close`。
- 计划 `L1311–1327`：失败残留分析及 Gateway 回收承诺。

**问题：**

`KeyboardInterrupt` 不属于 `Exception`，因此初始化握手期间的中断会绕过 `start` 中的清理。与此同时，`.start()` 没有返回，外层 `client` 的赋值尚未完成，仍然是 `None`，所以 `main` 的 `finally` 也不会清理已经启动的 Gateway。

这不是本次更改才引入的传输错误；对照上一版发现 `ce_mcp_client.py` 代码块完全相同。但它与当前“失败后只保留本地文件、自己的 Gateway 会被回收”的说明冲突。

**离线复现结果：**

用假 Popen 对象模拟 Gateway 已启动，在初始化 RPC 抛出 `KeyboardInterrupt`，经完整 `main` 路径观察：

```json
{
  "case": "ctrl_c_during_initialize",
  "exitCode": 130,
  "childOwnedByUnclosedClient": true,
  "stdinClosed": false,
  "waitCalls": 0,
  "terminateCalls": 0
}
```

复现没有启动真实进程；它证明退出路径没有调用相应清理，不能据此宣称真实 CE/游戏受到了修改。

**建议修订：**

最小修正是先保存客户端对象，再调用启动方法，使外层 finally 始终拥有清理对象：

```python
client = McpClient([str(gateway)], args.timeout, output / "gateway.stderr.log")
client.start()
```

同时考虑在 `start` 内对包含中断在内的失败进行清理并重新抛出，例如仅用于资源回收的 `except BaseException: self.close(); raise`；保持 `close` 幂等，且仍然只处理本脚本拥有的 Gateway。

增加 `main` 级别的启动中断测试，断言关闭管道并等待/回收自己创建的子进程。现有“未附加”测试只验证 `bind_target` 抛出异常，并非完整 CLI 生命周期测试，不能覆盖这一问题。

## 五、建议修订顺序

1. **先明确 R4 的交付范围**：9 条还是 13 条，统一地址表、固定列表、测试和完成标准。
2. **一起处理 R1/R2**：为收尾审计增加显式状态，并纳入统一结束流程，补齐故障测试。
3. **修复 R5 的启动对象所有权**：保证 start 尚未成功返回时也能清理，补上 main 级中断测试。
