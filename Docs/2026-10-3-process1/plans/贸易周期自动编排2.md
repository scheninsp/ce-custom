# 贸易周期自动编排2 实施方案

我将使用 writing-plans 能力生成完整实施方案

> **面向自动化执行人员：必须配套子能力：使用 superpowers:executing-plans 逐任务执行本方案。步骤使用复选框（`- [ ]`）用于进度跟踪。**

**目标：** 在九州新增五个贸易中心建成后的环境中，监测连续多个完整游戏周，回答同一商品一周刷新和容量调整的次数、调整函数及其调用栈，并验证上层批次的实际调度间隔。

**架构方案：** 先校准九州对象与候选州引用，再同时设置批次入口、Refresh 入口、增加提交、减少提交四个原生条件执行断点。CE 条件只筛选和生成事件，匹配后停下；Python 顺序持久化事件、采集调用栈后 Run，以真实游戏日期建立周窗口，另外安排写入验证阶段。

**技术栈：** PowerShell、Python 标准库、现有 CheatEngine MCP 网关、CE 7.7 原生 Complex 条件、Lua、CE 原生 StackTrace。

## 起点、既有结论和本次假设

- 旧实验已封存 `1884.8.25 → 1884.9.1`：九州木材 ID 10，方向 0 增加提交 1 次、商品量 15；减少提交 0 次；方向 1 无提交；条件错误 0；容量账本净变化一致。旧实验没有独立监控实际写入，也不能证明每周固定一次。
- 用户继续运行到 `1884.11.5`，九州新增的五个贸易中心均已建成，旧断点全部删除。本次从重新建断点开始；不沿用旧状态文件或旧计数器。
- 旧州指针 `0x3A484D9DB60`、旧容量地址 `0x3A484D9F8B8/0x3A484D9F8BC`、旧木材指针 `0x3A4012E4A60` 仅是查找线索。运行后容量、预算、表存储均可能变化，必须重新验证。
- 当前静态证据支持按州建立条目，共享州容量与商品表；没有已确认的“每个建筑/每个等级独立 Refresh”路径。先辨别用户所称五个中心是建筑等级、独立建筑对象还是其他实体；不能直接乘五或把州计数除以五。
- 假设 H1：每个实际监测对象、每个商品、每个完整周，Refresh 总调用数恰好 1。假设 H2：每方向、每阶段分别至多 1。两者分别检验，不能用 H2 的结果代替 H1。
- 假设 H3：`UpdateStateTrades` 的相邻调用间隔为七个游戏日。它属于任务调度链，入口本身不是已经证明的周时钟。

**已有证据提示 H1 很可能不成立。** 候选筛选先 Refresh，选中候选在执行前再 Refresh；同一批次还可重选多轮。新实验的任务是取得九州同一商品的动态反例与次数，而不是预设结果。

## 任务1：校准对象、候选引用和断点资源

**涉及文件：** 新建 `Scripts/ce_trade_cycle2.py`、`Scripts/ce_trade_watch2.lua`；复用原生条件及采集模块。

**接口依赖：** `McpClient.call`、`select_instance`、`validate_runtime`、`read_status`、`STATUS_COMPAT_SOURCE`、`NATIVE_STACK_SOURCE`。调用前检查现有函数签名，原样复用；不能把 `stateValid=false` 回执当成可靠运行状态。

**执行步骤：**

- [ ] 只读列出 CE 实例、PID、模块基址、构建、当前断点列表及影子列表，记录当前游戏日期 `1884.11.5` 是否仍成立、游戏自身是否暂停、调试器是否停止。

- [ ] 如果没有停止上下文，先从 CE 工具清单核对支持的暂停方法，以建立调试停点；记录此动作是调试暂停。不要把工具回执等同于已经停止，必须通过固定只读兼容查询确认 RIP/RSP/THREADID。

**接口依赖：** 任务1 config；原生条件 CLI 的 `--condition-file` 与后端 inspect/update。本次不是旧脚本的 prepare：旧脚本要求三个旧断点已经存在，且硬编码木材，不能直接运行。

**对外输出：** `prepare --state-file PATH` 导出四份 `.condition.lua`，逐个新建并 inspect 读回；CE 全局使用独立 `tradeCycle2`，不覆盖旧 `tradeCycleAgent`。watch 字段为 `id/state/tableAddress/stateRef/base/addresses/armed/batch/sequence/events/errors/lastError`。

| 正式地址 | 筛选 | 捕获内容 |
| --- | --- | --- |
| `victoria3.exe+131C2B0` | 不用 RCX/R14 按州过滤，这是上层多州批次入口 | 全局入口序号、日期、线程、入口返回地址；不采其他州商品 |
| `victoria3.exe+11FBDA0` | `readInteger(RCX+28)==stateRef` | 真正 Refresh 入口；商品、方向、模式、候选地址、入口 `[RSP]` 返回地址 |
| `victoria3.exe+11FD93B` | `RCX==state+1D88`，不筛商品 | 增加提交；商品 ID、RBP 方向、RBX 商品量、R8 容量步长 |
| `victoria3.exe+11FAF69` | 同上 | 减少提交；同样记录原始寄存器 |

**执行步骤：**

- [ ] 初始化 `tradeCycle2` 仅写 CE Lua 状态；`armed=false,batch=0,sequence=0,events={},errors=0`。当前实验 ID 必须唯一且与 config 一致，已有同名实验须先导出再明确归档，不能自动覆盖。
- [ ] 初始化 addresses 的键为 `boundary/refresh/add/remove`，数值由 `getAddress('victoria3.exe+...')` 解析。生成的四份条件均使用下列完整条件主体；初始化程序在第一段嵌入实际实验 ID 比较，缺失或不一致均返回 true 停下。

```lua
-- 记录原生断点的真实求值；只读游戏内存，匹配事件要求停下。
local w = tradeCycle2
if type(w) ~= 'table' then return true end
-- 校验和复制当前事件；无入参，返回是否停下，外层捕获英文错误。
local ok, stop = pcall(function()
    local kind = nil
    for name, address in pairs(w.addresses) do
        if RIP == address then kind = name end
    end
    assert(kind ~= nil, 'Unexpected breakpoint address')
    local candidate, goods, goodsId, direction, mode, caller = nil
    if kind == 'refresh' then
        assert(math.type(RCX) == 'integer' and RCX ~= 0, 'Invalid candidate')
        local ref = readInteger(RCX + 0x28)
        assert(ref ~= nil, 'Unreadable candidate state reference')
        if ref ~= w.stateRef then return false end
        candidate = RCX
        goods = readQword(candidate)
        direction = readBytes(candidate + 8, 1, false)
        mode = readInteger(candidate + 0x2C)
        caller = readQword(RSP)
    elseif kind == 'add' or kind == 'remove' then
        if RCX ~= w.tableAddress then return false end
        goods, direction = RDX, RBP
        assert(math.type(RBX) == 'integer' and RBX >= 0, 'Invalid quantity')
        assert(math.type(R8) == 'integer', 'Invalid capacity delta')
        -- 内部 call 之前的 [RSP] 不是当前函数返回地址，提交栈由原生展开取得。
    else
        caller = readQword(RSP)
    end
    if kind ~= 'boundary' then
        assert(math.type(goods) == 'integer' and goods ~= 0, 'Invalid goods')
        goodsId = readInteger(goods + 0x10)
        assert(goodsId ~= nil and goodsId >= 0, 'Invalid goods ID')
        assert(direction == 0 or direction == 1, 'Invalid direction')
        if kind == 'refresh' then
            assert(mode ~= nil, 'Unreadable candidate mode')
        end
    end
    if caller ~= nil then
        assert(math.type(caller) == 'integer' and caller ~= 0, 'Invalid caller')
    elseif kind == 'refresh' or kind == 'boundary' then
        error('Unreadable caller')
    end
    assert(#w.events < 100000, 'Event limit reached')
    local counted = w.armed
    if kind == 'boundary' then
        w.batch = w.batch + 1
        w.armed = false
        counted = false
    end
    w.sequence = w.sequence + 1
    local event = {
        sequence=w.sequence, kind=kind, counted=counted, batch=w.batch,
        ip=string.format('%X', RIP), sp=string.format('%X', RSP),
        thread=string.format('%X', THREADID), goodsId=goodsId,
        direction=direction, mode=mode,
        caller=caller and string.format('%X', caller) or nil,
        candidate=candidate and string.format('%X', candidate) or nil,
        goods=goods and string.format('%X', goods) or nil,
        quantityRaw=(kind == 'add' or kind == 'remove') and tostring(RBX) or nil,
        capacityDeltaRaw=(kind == 'add' or kind == 'remove') and tostring(R8) or nil
    }
    w.events[#w.events + 1] = event
    return true
end)
if not ok then
    w.errors = w.errors + 1
    w.lastError = tostring(stop)
    return true
end
return stop
```

其中 ID 比较由生成器在 `local w = tradeCycle2` 后生成 `if type(w) ~= 'table' or w.id ~= ... then return true end`，使用现有 `lua_quote` 编码 config 的真实 ID；不能留下人工替换字段。

- [ ] 每条匹配事件都停止，即使 armed=false 也保存为预热/诊断事件，不混入计数。过滤其他州时返回 false。正式阶段不采用不停下计数，确保调用栈可对应每个新事件。

## 任务3：采调用栈，顺序 Run，监测连续完整周

**涉及文件：** `Scripts/ce_trade_cycle2.py`、`Scripts/ce_trade_cycle2_report.py`。

**接口依赖：** config、watch 事件、固定只读状态查询与 `NATIVE_STACK_SOURCE`。新增命令合同：`inspect/prepare/seek/start/advance/mark-boundary/finish`，都接受 `--state-file`；正式阶段只有 `seek/advance` 能带 `--allow-run` 调用 `debugger_continue`，校准阶段按任务1的独立授权参数执行。`start/mark-boundary` 接收 `--date YYYY-MM-DD`；`finish` 不生成推算日期。

```text
monitoring --new boundary--> boundary_wait
```

- [ ] start 时在当前入口将 armed=true。左边界入口对应接下来执行的批次，计入左侧窗口；右边界到达时先封存之前事件，再决定是否把右侧入口作为下一窗口起点。入口自身单独计数，避免“边界事件 counted=false 导致批次数为零”。
- [ ] 每次 Run 前核验实例/PID/构建/对象/四个条件、错误数、当前停止事件序号；确认上一事件已原子落盘后才继续一次。Run 回执不代表完成，轮询停止状态与新的 sequence；同 RIP/RSP/线程但新 sequence 仍是新命中。

- [ ] 四周后若尚未观察到重复，或就业仍使预算继续变化，扩展到八周；若已有重复仍完成四周，以观察上层间隔及提交最大值。八周仍全为0/1仅给出观测结论，不宣称一般规律。若超时或事件上限达到，保存并停止，当前窗口标为不完整。

- [ ] 最后在右边界封存，保持停止且 armed=false。后续验证开始前另建阶段记录，不能把验证事件混入已完成周。

**要验证的栈形态（历史路径，实际栈允许有并行任务包装）：**

```text
增加提交 +11FD93B
  TryAdjustStateTrade +11FD470
  UpdateStateTrades +131C2B0
  州贸易任务适配 +1319B40
  回调适配 +7C49D0 -> 任务执行 +7B81E0 -> Tick任务列表 +7BE1B0
```

并行 worker 的原生栈可能不包含发起任务线程的 UpdateStateTrades；用入口区间、线程、准备阶段调用点及任务包装证据关联，不能把跨线程关系伪造为单线程完整栈。若上一批次 worker 可能未完成就出现新入口，保留关联歧义，增加任务完成/同步点验证后才逐批归属。

**上层周期验证：** 用全部批次入口日期计算间隔，并统计每个周窗口内实际入口数。连续四周均七天且每周一次，只能证明该环境这四周的观察结果。要补静态排程证明时，从已知 `+1319B40 → +131C2B0` 反追任务注册、`+7B6ED0` 等任务构造及日期门禁，采集比较/分支证据；减少保护期的 `8×168` 常量不能当成 Refresh 周期。

## 任务4：独立核实写入和调整次数上界

**涉及文件：** `Scripts/ce_trade_cycle2.py`、`Scripts/ce_trade_cycle2_report.py`；新证据写入实验目录 `write_validation/`。

**接口依赖：** 正式提交事件与账本快照；`+1027970`、`+1027A40` 已保存反汇编。验证只针对九州，优先选择四周内提交最多的商品，木材单列。

**对外输出：** 每次提交的执行落实证据、逻辑调整次数与底层 store 次数对照、观察最大值及条件性预算上界。

**执行步骤：**

- [ ] 正式阶段提交停点记录目标表、商品 ID、存在位、存储基址、槽位值和 R8。在下一停止现场读取账本，用逐事件预期变化核对；这是账本核对，不能单独称为独立写断点证据。
- [ ] 增加提交 `+11FD93B` 应 call `+1027970`，减少提交 `+11FAF69` 应 call `+1027A40`，先逐字节核对。`TryAdjustStateTrade +11FD470` 作决策；`RemoveOneTradeUnit +11FAF20` 执行减少路径；`Refresh +11FBDA0` 做估算，不是账本容量调整函数。
- [ ] 初步落实验证采用顺序 Step Over 提交 call（先核对现有 `ce_run_step_over.py` 的合同），只在独立验证阶段执行，保存调用前与返回后同表同商品值。一次 call 前后变动是落实证据，可能包含多个机器写入；不计为“一个实际 store”。
- [ ] 要独立计机器写入时，在验证阶段停用并清理本实验 Refresh 断点，用空出的槽在当前已存在的商品容量槽位 `readQword(table+8)+goodsId*8` 上设8字节 On Write/Break 硬件断点；保留边界、增加提交、减少提交。先检查有效存在位和对齐，不能给不存在的槽设置旧地址。
- [ ] 每个提交前重新读取存储指针与存在位。存储变化、释放或新建商品表项立即停止、重算地址并重新安装；失效地址上的零命中不能证明没有写入。若安装版写断点能力不能读回或资源冲突，记录限制，采用 Step Over 核对，不伪造写断点完成。
- [ ] 写断点命中保存原生栈和写指令。数据断点通常在写指令执行后停下，核对前一条指令及实际槽位，不直接把当前 RIP 当作 store 地址。预期增加表更新包含 `+1027A01/+1027A1C`，减少表更新包含 `+1027AD6/+1027AF1`；两者分支不同，实际以当前反汇编与现场为准。
- [ ] 写入实验至少覆盖实际出现的每种增/减操作；没有减少样本时报告“减少写入路径未动态验证”。一周不足可延长验证一至两周，不改商品评分或容量制造事件。验证阶段缺少 Refresh 断点，其数据不能用于完整 Refresh 次数判断。
- [ ] 汇总口径分开：增加次数 A、减少次数 R、容量调整动作数 A+R、成功尝试数（替换可含两动作但只消耗一次预算）、商品量求和、容量净变化、机器写入数。净变化0也可能 A/R 都非0。
- [ ] 正常路径单位为定点100000：增加 delta=方向1的+100000或方向0的-100000；减少执行 `old-R8`，必须按 Sub 函数语义计算，不能把两种提交的 R8 直接同号相加。
- [ ] 每次 UpdateStateTrades 的九州条目初始预算为 B，若确认普通成功每次扣1、预算不补充，则单州成功尝试≤B；保守的同商品增加≤B、减少≤B、动作合计≤2B。多批次一周则按该周各批次 B 求和；记录初始化标志与所有预算变化，出现补预算或其他路径时撤销此界限。
- [ ] 此上界不是“一周一定调整这么多”，也不限制 Refresh 次数；失败后重评估及其他州推动轮次会增加刷新。报告实际四周/八周最大值、发生窗口及商品，与上述条件性上界并列，不宣称取得所有市场状态下的全局最大值。
