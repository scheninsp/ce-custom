# 绕过贸易保护期的情况

## 结论

减少候选函数 `victoria3.exe+122AC50` 有一个布尔参数 `bypassProtection`。普通自治贸易选择从 `+131D540` 调用它时传入 `false`，会执行增加后 8 周的保护期判断；另一些容量调整路径传入 `true`，会跳过该判断。

这里的 8 周是 `8 * 168` 个游戏小时，即 56 个游戏日。保护条件的语义是：商品最近增加后，在保护期结束前通常不能被选作减少候选。

## 保护参数的直接证据

`+122AC50` 入口把第 4 个参数 `r9d` 保存为保护参数：

```asm
+122AC53  mov [rsp+20], r9d
+122AC71  mov ebp, r9d
```

枚举已有贸易时，函数先检查保护参数，再决定是否执行日期检查：

```asm
+122AD3E  test ebp, ebp
+122AD40  jne  +122AE7A
```

`ebp != 0` 会跳过日期检查，继续构造和刷新减少候选。未绕过时，判断当前时间是否小于“上次增加时间 + 8 * 168”，满足则跳过该商品。

这里的 `SelectReductionCandidate` 沿用既有分析名称，对应 `victoria3.exe+122AC50`；`bypassProtection` 也是分析用参数名。

## 已确认的绕过调用路径

### 容量重平衡路径

调用链为：

```text
UpdateStateTrades(+131C2B0)
  -> +13260F0
    -> +122B9A0
      -> +122BD40
        -> +122AC50(..., bypassProtection=1, ...)
```

`+122B9A0` 会计算贸易中心容量和已用容量。触发条件可进一步收紧：

- `+122B9C7` 写入可用容量 `state+1D58`，`+122B9DA` 写入已用容量 `state+1D5C`。
- `+122BA8E` 将已用容量减去可用容量，得到初始超额容量。
- 随后的商品资格清理会移除一些已有贸易，并在 `+122BBCF` 从超额容量中减去相应整数容量。
- 只有清理后剩余超额容量大于 0，才在 `+122BCB8..+122BCE9` 调用 `+122BD40`，传入需要继续减少的整数容量。

`+122BCBD` 的 `ebx *= state[+8]` 用于构造随机种子，不是计算容量上限。前面对话曾将它解释为容量计算，此处更正。

`+122BD40` 在调用 `+122AC50` 前明确执行：

```asm
+122BDC5  mov r9d, 1
+122BDD9  call +122AC50
```

因此该路径可以把尚未满 8 周的已有贸易纳入减少候选。其高可信业务解释是：**重算后仍超过容量上限，强制削减已有贸易以恢复容量约束。** 普通满容量本身不满足这个条件，必须是清理后的已用容量仍大于可用容量。

### 直接贸易效果路径

另一条调用链为：

```text
+17B4EE0 / +17B5020
  -> +17B53F0
    -> +122BD40
      -> +122AC50(..., bypassProtection=1, ...)
```

`+17B4EE0` 和 `+17B5020` 属于同一组贸易效果实现。二进制中存在以下 RTTI 和字符串：

```text
CChangeTradeEffect<...>
IncreaseTrade
set_imports
set_exports
add_imports
add_exports
remove_imports
```

游戏脚本也实际使用了这些效果，例如 `game/common/history/trade/00_historical_trade.txt` 中有 `add_imports` 和 `add_exports`。

`+17B53F0` 要求调整量为正；调用 `+17B5570` 处理商品方向后，比较请求增加的整数容量与当前空闲容量：

```asm
+17B54A5  mov esi, [rdi+1D58]
+17B54AB  sub esi, [rdi+1D5C]
+17B54B1  cmp esi, ebx
+17B54B3  jge  +17B5522
```

当空闲容量 `esi` 小于请求调整量 `ebx` 时，函数计算缺少的容量并调用 `+122BD40`：

```asm
+17B5501  mov edx, ebx
+17B5503  sub edx, esi
+17B5512  call +122BD40
```

`+122BD40` 再以 `r9d=1` 调用减少选择函数。因此，直接增加进口或出口的效果在空闲容量不足时，会先尝试强制减少已有贸易，这一步可以绕过 8 周保护。

例如空闲容量为 2，效果请求增加 5，则传给 `+122BD40` 的削减次数是 3。该函数逐次选择减少候选并调用 `+11FAF20` 移除一单位；若没有有效候选会提前退出。因此“允许绕过”不等于每次都必然削减足额。

`+17B53F0` 的 `r9b` 保存到 `r14b`，用于后续正负方向选择；它与 `+122AC50` 的保护参数不是同一个业务参数。不能把效果入口的 `r9b=0/1` 直接解释成是否绕过保护。

## 业务解释与证据边界

目前最有证据支持的解释是：

1. **普通自治调整**遵守 8 周保护，防止刚增加的贸易立即被评分波动反向撤销。
2. **容量重平衡**优先保证容量账本和上限约束，必要时允许减少受保护贸易。
3. **脚本/效果驱动的直接增加**试图满足请求的容量增量；空闲容量不足时可以强制清理已有贸易。游戏历史配置中的 `add_imports`、`add_exports` 提供了此效果族实际使用的例子。

可以确认存在这些绕过参数和调用条件，但尚不能仅凭静态代码断言每个具体事件、决议或外交操作都使用该路径。`CChangeTradeEffect` 的 RTTI、`IncreaseTrade` 和 `goods_effects.cpp` 字符串支持其贸易效果归属，但各模板类型对应的全部注册名称仍未完全恢复。`set_imports`、`set_exports`、`remove_imports` 等字符串证明效果族存在这些接口，不能单凭字符串就断言每个接口都会经过这条缺容量削减路径。

容量下降的具体原因，例如就业减少、生产方式变化或接入度变化，应另行追溯容量计算函数；这里只确认“重算后超容量”的条件，不把这些具体原因列为已验证触发。

因此，准确表述应为：**8 周保护适用于通常的自治减少候选；容量重平衡和容量不足时的直接贸易效果调整可以通过 `bypassProtection=true` 跳过保护期。**
