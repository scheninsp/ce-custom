# 周期推算操作步骤指南

编写日期：2026-10-03（北京时间）。本指南用于观察“指定州/贸易中心、指定商品，在一个游戏周内发生多少次贸易增减”。这里只提供步骤，没有执行断点配置、Lua 计数或游戏推进。

## 一、先明确统计目标

每次实验记录一个州、一个商品，并分别统计：进口增加次数、进口减少次数、出口增加次数、出口减少次数，以及各类调整对应的商品量之和。

不要把以下数值混为一谈：

- Refresh 次数：包括没有成交的候选评估，不能代表调整次数。
- 调整提交次数：进入州商品容量账本修改调用的次数，本指南首先统计这个数。
- 实际写入次数：通过商品槽位 Write 监控交叉核对，排除调用中途返回等情况。
- 周前后净变化：增加与减少可能抵消；净变化为零不代表没有调整。

已分析路径是按州建立条目、循环选择候选并逐州调整，同时维护共享市场和全局统计。不是已经确认的“市场先确定一个总量，再一次性分配到各中心”。方向 0 对应进口、1 对应出口是当前高可信解释，仍建议用一次已知方向的实际变化确认。

依据：[调用周期分析](刷新候选函数调用周期分析.md)、[数量输出分析](刷新候选函数进出口数量输出分析.md)、[多轮调整分析](../goal3_static_disassembly4.md)。

## 二、准备目标信息并确认暂停状态

1. 确认 CE 当前附加到正确的 Victoria 3 进程，记录 PID、模块基址和程序版本/构建信息。
2. 记录游戏当前日期、时刻、速度与暂停状态。正式测量前，优先使用游戏自身暂停，让当前更新完成后再准备计数。
3. 如果 CE 正停在调试断点，需要确认现场位置。游戏暂停、进程挂起、调试断点暂停是三种不同状态，不能相互替代。
4. 找到目标州指针 `state` 和目标商品对象 `goods`，核对 `goods+0x10` 的 4 字节商品 ID 与名称。
5. 计算州商品容量表 `table = state + 0x1D88`，确认地址可读。
6. 确认两个拟用断点地址没有用户已有断点、采集任务或其他脚本回调；若存在冲突，不直接覆盖。

历史九州样本是 `state=0x3A484D9DB60`，对应 `table=0x3A484D9F8E8`；这些地址必须重新确认，不能默认在新进程有效。已验证木材 ID 为十进制 10；这不是硬木 ID，也不能按配置顺序推算其他商品 ID。

## 三、配置两个调整提交断点

| 断点表达式 | 含义 | 此处需要记录的寄存器 |
| --- | --- | --- |
| `victoria3.exe+11FD93B` | 增加贸易分配，调用州商品容量表的增加函数 | `RCX` 表地址、`RDX` 商品对象、`RBP` 方向、`RBX` 商品量定点值 |
| `victoria3.exe+11FAF69` | 减少贸易分配，调用州商品容量表的减少函数 | `RCX` 表地址、`RDX` 商品对象、`RBP` 方向、`RBX` 商品量定点值 |

这两个位置的 `RBX / 100000` 是本次商品量 q；`R8` 是带符号的容量步长，不是 q。它们是调用前的执行断点，因此首先得到的是提交路径计数，不应未经写入验证就命名为“成交次数”。

依据：[增加路径](../../Output/goal3_static_20261002/function_7FF777CED470.md)、[减少路径](../../Output/goal3_static_20261002/function_7FF777CEAF20.md)。

用模块相对表达式定位并核对实际指令。两个位置分别应是调用 `+1027970` 和 `+1027A40` 的指令；游戏更新后如果机器码不符，先停止实验。

## 四、初始化计数器并设置 Complex 条件

先在 CE Lua 窗口执行初始化；必须替换实际表地址和商品 ID：

```lua
tradeWatch = {
    table = 0x3A484D9F8E8,
    goodsId = 10,
    armed = false,
    counts = {},
    raw = {},
    errors = 0
}
```

初始化会重置这个实验计数器。若已有未导出的同名实验，先导出，不能直接覆盖。

在 Memory Viewer 的 Breakpoints 列表中，对两个代码断点分别设置以下相同的 Complex function 条件。不要把整段代码填进 Easy formula：

```lua
if tradeWatch and tradeWatch.armed and RCX == tradeWatch.table then
    local goodsId = readInteger(RDX + 0x10)
    local operation = nil
    if RIP == getAddress("victoria3.exe+11FD93B") then
        operation = "add"
    elseif RIP == getAddress("victoria3.exe+11FAF69") then
        operation = "remove"
    end
    if goodsId == nil then
        tradeWatch.errors = tradeWatch.errors + 1
    elseif goodsId == tradeWatch.goodsId then
        if operation and (RBP == 0 or RBP == 1) then
            local key = operation .. "_" .. tostring(RBP)
            tradeWatch.counts[key] = (tradeWatch.counts[key] or 0) + 1
            tradeWatch.raw[key] = (tradeWatch.raw[key] or 0) + RBX
        else
            tradeWatch.errors = tradeWatch.errors + 1
        end
    end
end
return false
```

`return false` 表示这个原生条件不要求停下；匹配目标时仍会累计计数。Lua 条件不能编译、寄存器语义不符或出现 errors 时，不能把输出当成完整的周统计。本代码按已有反汇编编写，尚未在游戏中实测。

注意：这里的 Complex 条件返回规则与 Lua 断点回调的返回规则不同，后续 Python 自动化不能把这个 `return false` 直接照搬为回调自动继续逻辑。

## 五、可选：用 Write 核对实际写入

州商品容量表的值槽位计算方式为：

```text
storage = readQword(table + 0x08)
slot = storage + 商品ID × 8
```

只有在存储有效、该商品存在位有效时，槽位中的 8 字节才可作为有效值解释。表值是带方向的容量分配，不是最终 UI 商品量。

在该槽位上选择 Find out what writes。它的地址已筛选了州和商品，通常不需要再加同样的筛选条件。普通访问/写入断点可以通过 Breakpoints 列表设置条件；DBVM 特殊模式不能直接套用，菜单不可用时先核对后端。

已知值写入点：

| 操作函数 | 写入指令 |
| --- | --- |
| 增加函数 `+1027970` | `+1027A01`、`+1027A1C` |
| 减少函数 `+1027A40` | `+1027AD6`、`+1027AF1` |

每组中的两个地址是不同写入分支，应统计实际命中的分支。其他写入指令单独归档，并核对调用来源；不能因为是容量槽位写入就都归入本次周调整路径。

表存储可能重新分配。实验前后需重新读取 `table+0x08`，如果发生迁移，固定槽位监控可能漏写，不能据此给出完整计数。也不要同时累计州表、方向表、市场表和全局表来算调整次数：同一次调整会更新多个表。

## 六、正式推进一个游戏周

1. 保持游戏暂停，确认两个条件配置完成、计数器未启用且为空，记录起始游戏日期/时刻和相关值。
2. 执行 `tradeWatch.armed = true`，作为本实验开始记录的标志。
3. 若 CE 停在调试断点，使用 CE 的 Run 继续调试执行；如果游戏自身仍处于暂停，还需另外恢复游戏时间。
4. 推进一个完整游戏周。优先在相同日期相位开始/结束，不用现实时间的固定秒数代替游戏周。
5. 到终点先暂停游戏并确认当前更新完成，再记录结束日期/时刻，执行 `tradeWatch.armed = false`。
6. 读取统计并保存，最后删除本实验新增的两个代码断点、关闭本实验的写监控，不动原有断点。

若已经停在贸易调整内部，恢复执行可能只采到本批次的后半段。这种结果要标为部分批次，不与完整周实验混合。

如果人工暂停晚了，按实际日期跨度记录，不能仍标成“恰好一周”。若以后用脚本轮询游戏日期，同样必须记录轮询越界量；精确截止还需要经过验证的时间边界控制。

## 七、读取结果并推算

在 CE Lua 窗口执行：

```lua
for _, key in ipairs({"add_0", "remove_0", "add_1", "remove_1"}) do
    print(string.format("%s count=%d quantity=%.5f",
        key,
        tradeWatch.counts[key] or 0,
        (tradeWatch.raw[key] or 0) / 100000))
end
print(string.format("errors=%d", tradeWatch.errors))
```

`add_0/remove_0` 分别是方向 0 的增加/减少；`add_1/remove_1` 分别是方向 1 的增加/减少。每个方向的提交净商品量是“增加累计量减去减少累计量”，不要把两个方向混成一个总数。

这仍不自动等于 UI 显示值的最终变化：需要确认提交确实写入，以及内部表到 UI 的映射、数量修正变化等因素。保存 Write 的各指令 Count、开始/结束表值和 UI 数值，交叉核对。

一个游戏周只提供这段窗口内的次数。要判断稳定周期，建议连续记录至少三个完整周，并另记录 `+131C2B0` 批次入口的游戏时间；不能用现实时间间隔、Refresh 次数或“只测一次”证明严格周排程。

## 八、实验结果至少保留哪些信息

保留进程 PID、CE 实例与模块身份、州指针、商品对象/ID/名称、表地址及前后存储指针、起止游戏日期/时刻、四类次数及商品量、errors、写监控 Count、是否完整覆盖周/批次，以及本次创建和清理的断点。

零次也是可能的业务结果，但只有在目标校验通过、计数器确实启用、断点有效、观察窗口完整且没有错误/漏采时，才能将其解释为“本周没有调整”。
