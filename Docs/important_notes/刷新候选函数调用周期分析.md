# Refresh（+11FBDA0）的调用周期分析

分析日期：2026-10-03（北京时间）。本次仅使用已有反汇编、已记录的断点现场和本地程序文件进行静态核对；没有继续游戏、单步、设置断点或修改游戏内存。

## 1. 结论

**结合已知的周调用观测，Refresh 可以高可信地归入“每周贸易调整批次中的按需重算函数”，但不能说它本身严格每周只调用一次。**

需要区分两种含义：

- **批次周期**：已观测到的九州贸易调整路径按游戏周触发，Refresh 位于该路径内，因此会随周贸易调整执行。
- **函数调用次数**：一个批次内，选候选会对多个商品/方向分别调用 Refresh；尝试执行调整时又会刷新选出的候选；上层还可以进行多轮调整。因此一次游戏周内可以出现多次 Refresh，并非固定一次。

对于某一个指定商品、指定方向，是否在这一周调用、调用多少次，还取决于筛选、保护期、候选有效性、州是否进入条目数组以及剩余调整预算。不能据此承诺“每个商品每周恰好刷新一次”。

严格的静态排程证明尚未闭合：现有证据没有恢复贸易任务注册处的周条件，也没有排除其他调用路径或初始化调用。

注意：原始 Count 统计的是“某条指令访问九州这一个字段地址的次数”。它不会计入函数中途返回的执行，也不代表其他州的调用次数。即便接受这些函数按周工作的已知前提，也不能把这种字段 Count 原样传递为全部下游函数的 Count。

## 3. 最强证据：Refresh 就在周读取点之前

来源：[+11FD470 反汇编](../../Output/goal3_static_20261002/function_7FF777CED470.md)。

| 指令位置 | 内容 | 含义 |
| --- | --- | --- |
| `+11FD58F` | `je +11FD5A2` | 减少候选无效时跳过第一次刷新 |
| `+11FD596` | `lea rcx,[rdi+F8]` | 减少候选作为 Refresh 的第一个实参 |
| `+11FD59D` | `call +11FBDA0` | 刷新减少候选 |
| `+11FD5AC` | `je +11FD5BB` | 增加候选无效时跳过第二次刷新 |
| `+11FD5B3` | `mov rcx,rsi` | 增加候选作为第一个实参；此前 `rsi = rdi+B0` |
| `+11FD5B6` | `call +11FBDA0` | 刷新增加候选 |
| `+11FD5BB` | `mov eax,[r14+1D5C]` | 已知每周 Count +1 的已用容量读取点 |
| `+11FD5C9` | `mov eax,[r14+1D58]` | 已知每周 Count +1 的可用容量读取点 |

这两个调用都不是另一个日期判断分支中的异步调用，而是同一次州贸易调整中、读取容量之前的同步调用；是否执行由对应候选的有效性检查决定。

因此：

- 已观测的周调整路径直接包含 Refresh，不是仅仅根据函数名猜测它按周参与。
- 一次到达容量读取点的调整，执行阶段最多调用两次 Refresh；两槽均有效时调用两次。
- 仅根据读取点 Count +1，不能确定两槽中究竟哪一个有效，也不能排除本周还有选候选阶段的 Refresh。

## 4. 选候选时已经调用过 Refresh

已有静态文件中至少存在以下四个直接调用点；这不是整个程序的完整交叉引用枚举。

| 调用点 | 所在函数 | 调用对象与位置 |
| --- | --- | --- |
| `+122AEBB` | `+122AC50`，`SelectReductionCandidate` | 遍历已有贸易，对通过数量/保护期条件的商品建立临时候选并刷新 |
| `+122B53C` | `+122B320`，`SelectIncreaseCandidate` | 遍历商品和两个方向，对通过前置筛选的临时候选刷新，再检查增加门槛 |
| `+11FD59D` | `+11FD470`，`TryAdjustStateTrade` | 刷新已选出的减少候选 |
| `+11FD5B6` | `+11FD470`，`TryAdjustStateTrade` | 刷新已选出的增加候选 |

依据：[减少选择函数](../../Output/goal3_static_20261002/function_7FF777D1AC50.md)、[增加选择函数](../../Output/goal3_static_20261002/function_7FF777D1B320.md)。

`+131D540` 的工作体先在 `+131D693` 调用减少选择函数，再在 `+131D6D4` 调用增加选择函数，把结果分别复制到条目 `+F8`、`+B0`。随后执行阶段的两次 Refresh 是重新计算，不是本批次第一次计算候选。

依据：[+131D540 反汇编](../../Output/goal3_static_20261002/function_7FF777E0D540.md)。

这也意味着，不能把入口参数 `c` 当成跨周稳定不变的对象来解释周期：选择阶段刷新的是栈上的临时候选，执行阶段刷新的是条目中的已选候选。它们可以对应同一个州、同一个商品，但不是同一个内存对象。

## 5. 同一批次还可以循环多轮

来源：[+131C2B0 / UpdateStateTrades](../../Output/goal3_static_20261002/function_7FF777E0C2B0.md)。

- `+131D170` 调用候选准备批处理 `+1326280`；串行工作体为 `+131D540`。
- `+131D219` 调用 `+11FD470` 尝试一次州贸易调整。
- `+131D21E` 用 `or r12b,al` 累积本轮是否成功调整。
- `+131D27F` 检查这个成功标志。
- 若本轮存在成功调整，`+131D289` 跳回 `+131CEB0`，继续剔除预算耗尽条目、准备候选并尝试下一轮。

**这里的“下一轮”是同一次 UpdateStateTrades 内部的计算循环，不是等待下一游戏周。** 某个州是否参与后续轮次，还取决于它是否仍在活动条目数组中。

因此，对指定州的一次贸易更新批次，可以按如下方式理解总调用数：

`Refresh 总次数 = 各轮减少候选评估次数之和 + 各轮增加候选评估次数之和 + 各轮执行阶段有效候选数之和`

原始样本中 `+11FD5C9` 每周 Count +1，说明九州该容量读取点在观测窗口内每周命中一次；它不否定本批次候选搜索已经调用了很多次 Refresh，也不否定其他州可能进行了多轮调整。

## 6. 为什么现在还不能宣称已经静态证明周排程

已有调用链为：

```text
+137C990
  → +7D6400
    → +7BE1B0（Tick 任务列表）
      → +7B81E0（任务执行）
        → +7C49D0（回调适配）
          → +1319B40（州贸易任务适配）
            → +131C2B0（UpdateStateTrades）
              → 候选准备和循环调整
                → +122AC50 / +122B320 / +11FD470
                  → +11FBDA0（Refresh）
```

这条链有历史断点现场、展开信息和虚调用目标核对作为依据，详见 [goal3_static_disassembly.md](../goal3_static_disassembly.md)。但“属于 Tick 任务”不等于“每个 Tick 都执行”，也不自动等于“每周一次”。

目前缺少的是：任务列表构造（已有资料提到 `+7B6ED0` 等入口）、贸易任务注册/Prepare、以及可能的任务内部日期门禁中，究竟在哪一处决定本周是否执行 `+131C2B0`。因此不能给出固定星期几、一天中的具体时刻，或无条件断言初始化阶段也保持相同周期。

另外，`+122AC50` 中“上次增加日期 + 8 × 168”的判断是商品减少保护期；不能用这个常量证明 Refresh 每隔 168 个时间单位执行一次。Refresh 自身 `+11FBDA0..+11FC07C` 的已见指令也没有表现出一个控制入口频率的每周日期门禁；它的主要职责是按输入候选重算数量、优势及评分。

Refresh 图的 1015 条指令包含沿尾跳收录的 `+11FC320`；PE 异常表中 Refresh 自身的范围是 `+11FBDA0..+11FC07C`（右端不包含）。本次磁盘一致性核对不是重新读取当前进程内存，也不是新增运行时周期观测。

若只继续静态分析，优先追贸易任务的排程/Prepare 到 `+131C2B0` 之间的日期条件，而不是继续展开 Refresh 的评分下游。

若以后允许运行时验证，建议分别统计：

1. `+131C2B0` 的进入时间，确认批次间隔与星期位置。
2. `+11FBDA0` 的调用时间、返回地址、候选 `+28` 的州引用、商品和方向。入口 `RCX` 是候选而不是州；不能直接套用容量读取点的 `R14 == 州指针` 条件。
3. 按 `+122AEC0`、`+122B541`、`+11FD5A2`、`+11FD5BB` 四个已知返回地址区分减少评估、增加评估、执行前减少重算和执行前增加重算；其他返回地址单独归档。

最终建议采用的描述是：**“Refresh 随周贸易调整批次按需执行，一个批次内可能多次重算；周周期来自已观测的上游贸易更新路径，不是 Refresh 自身每周只执行一次的保证。”**
