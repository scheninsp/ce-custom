# 贸易周期自动编排实施方案

我将使用 writing-plans 能力生成完整实施方案

> **面向自动化执行人员：必须配套子能力：使用 superpowers:executing-plans 逐任务执行本方案。步骤使用复选框（`- [ ]`）用于进度跟踪。**

**目标：** 脚本接管 CE 条件核验、提交计数、Run、等待及证据导出，用户仅负责游戏自身暂停及周边界日期确认。

**架构方案：** 复用现有 MCP 客户端和只读状态兼容查询；在原生条件中写入 CE 侧事件序号，避免重复采集和相同 RIP 的新命中混淆。Python 持久化编排阶段，逐次核验后继续；边界、未知断点、错误和超时均停止自动推进。

**技术栈：** Python 标准库、现有 CheatEngine MCP 网关、CE 7.7 原生条件 UI、Lua 5.3、unittest。

## 全局约束

使用中文进行对话输出。使用中文进行代码注释，但是不要使用中文日志。
python,powershell等脚本代码文件，需要在文件头部使用中文注释说明文件功能。每个函数头部都要加上函数功能，以及入参与返回值的中文注释说明。
文件修改通过专用 apply_patch 工具完成。
用户已明确授权自动 CE Run；不写游戏内存，不调整游戏时间、速度，不自动解除游戏自身暂停。
不删除断点、不替换调试器 callback、不覆盖未知条件；只对本实验三个地址执行带旧值比较的条件更新。
状态查询复用已解决的固定只读 Lua 兼容流程。对象身份沿用本进程已确认目标，进程/对象变更时停止，不能凭可读自动认定九州。

### 任务2：CE 侧事件序号及 Python 阶段编排

**涉及文件：** `Scripts/ce_trade_watch.lua`、`Scripts/ce_trade_cycle.py`。
**接口依赖：** `McpClient.call`、`select_instance`、`validate_runtime`、`read_status`、任务1 request 模式。
**对外输出：** 六个 CMD 子命令和逐请求 JSON 证据；状态文件保存实例、进程指纹、模块基址、原始条件、实验 ID、阶段、最后处理序号及窗口起止快照。
**执行步骤：**
- [x] inspect 在停止现场采集九州容量、木材 ID/键名、存在位和有效容量槽位，回读三个原生条件。原始寄存器保存十六进制字符串，商品量整数保存十进制字符串。
- [x] prepare 创建唯一 CE 全局实验且 armed=false；三个地址只更新已读回的旧值。边界条件无筛选；两个提交条件只匹配州表和商品。真实条件求值生成递增序号，匹配仍返回 true；缺对象和异常也停下。
- [x] seek 从已知诊断停点或目标提交点继续，到下一边界停下；诊断停点只读记录并验证州。start 仅在新边界处接受人工 `--date YYYY-MM-DD`，启用统计。
- [x] advance 每次核对会话/对象/三个原生条件/计数器错误，再调用一次 Run。轮询状态和事件序号，不能仅凭 RIP 相同认定没有继续，或凭 Run 回执就当完成。
- [x] 目标命中保存后继续；诊断点核对 R14 后保存继续；边界停下、解除 armed 并等待日期确认。不自动把相邻入口称为一周。
- [x] finish 要求 end-start=7 天，核对逐事件 count/raw/errors 和容量账本，报告仅是提交次数，不冒充实际写入次数。每个异常保留状态及证据，禁止盲重发 Run。
- [x] 总等待秒数、轮询间隔和最大停点数均有限；超时不再 Run，不偷偷 Pause，明确目标可能仍运行。

阶段合同：
```text
prepared --seek--> start_wait --start(date)--> counting
counting --advance--> end_wait --finish(date,+7days)--> complete
任何失败：保存证据，停止推进，不清理或覆盖旧实验
```
